🔧 agent-r2g：把「开源 RTL-to-GDS 全签核」封装成 Claude Code Agent Skill——682 个设计规模验证，ORFS 通过率 96.2% / RCX 99.85%，并带 A/B 门控的自学习配方晋升闭环

这是目前公开可见工程完成度最高的 EDA Agent Skill 套件：用户装好技能后，只需对 Claude 说"set up the EDA tools"，再说"synthesize this UART at 100 MHz on nangate45"，即可从环境安装一路跑到通过 DRC/LVS/RCX 签核的 GDSII，输入既可以是自然语言规格、也可以是已有 RTL。
① 三个子技能（安装到 ~/.claude/skills/）：
· eda-install（SKILL 0）：探测机器、安装并校验工具链，提供三条路径——共享 EDA 服务器 / 源码构建 ORFS / OSS-CAD-Suite + 独立 OpenROAD 二进制；无 sudo 场景可走 Miniconda（litex-hub 频道）装 iverilog / magic / netgen / sky130A PDK；
· signoff-loop（SKILL 1）：RTL→GDS 主流程 + 签核 + 自我改进学习循环；
· def-graph（SKILL 2）：从已签核的 DEF/LEF/SPEF 提取 PyG 格式图数据集——并且明确拒绝为未签核设计建数据集，从源头堵住"用垃圾布局训 GNN"的数据污染问题。
② 自学习闭环（engineer_loop）：双记忆库设计——knowledge.sqlite 作为学习器的唯一输入（诚实门），journal.sqlite 只做操作取证、不被学习器读取；engineer_loop.py 无人值守驱动"拉设计 → 跑流程 → 签核修复 → 入库 → 学习 → A/B 门控 → 晋升/降级 → 未知症状升级"。配方生命周期为 shadow → candidate → promoted，只有 A/B 测试胜出才允许晋升。
③ 工程细节值得后端工程师注意：extract_route.py 识别布线拥堵中止信号，route_relief 自动降 CORE_UTIL 重跑（sky130hd 上清掉 18/25 个拥塞设计）；已吸收 6 项论文改进并通过 A/B 门控（密集奖励 outcome_score、方差感知 A/B、r2g-bench 留存测试、视觉辅助 DRC、预综合 KNN、后端感知综合重调）；所有签核检查器由 _bounded_run.sh 进程组托管，防孤儿进程。
④ 规模与平台矩阵：682 个 RTL 设计（ICCAD / RISC-V / BOOM / VTR 等）验证，1390 个 pytest；ORFS 后端 476/495 通过（96.2%）；签核语料 LVS 607/674 干净（90%）、DRC 675/682 诚实裁决（99%）、RCX 681/682（99.85%）；精选 70 设计子集 ORFS+LVS+RCX 100% 通过。支持 nangate45 / sky130hd / sky130hs / gf180 / ihp-sg13g2；明确不支持 asap7（社区 KLayout deck 误报、无 LVS deck）。
本周更新（08-02）：re-vendor R2G2.0 v2（层次分隔符 → 实例名映射）；修复 A/B judge 把"无证据 signoff 臂"误判为 SUCCESS 的裁决漏洞（failure-patterns #32c）；修正 Platform Support Matrix 对 gf180/ihp 签核能力的过度宣称（#32b）；gf180 轮次知识库快照（WAL checkpoint）。
核心看点：与本站已收录的 siliconcrew（自然语言→GDSII）、silica-eda（EDA 工具 MCP 封装）、pyslang-mcp（只读语义校验）相比，agent-r2g 补上了最缺的一环——可审计的签核裁决 + 用 A/B 实验管住"智能体自我改进"。它把"Agent Skill"从提示词集合升级为带诚实门、门控晋升与失败模式编号的工程系统，是开源 EDA 智能体从 demo 走向可复现基础设施的关键样本。

🔧 ECOS Chip Compiler 引入「flow agent foundation」——国产开源 RTL2GDS 编译器补上智能体地基，同步新增 soc-mpc 模板与 ics55 国产 PDK 流水线

ECC（ECOS Chip Compiler）是 ECOS 团队维护的开源芯片设计自动化方案，以工程化的"芯片编译器"形态整合 Yosys（综合）、ECC-Tools（自研 P&R 后端）、DreamPlace（布局）、KLayout（版图查看），完成 RTL→GDS 全流程；提供 ecc CLI 与 chipcompiler Python API 两种用法，并用 Nix 保证可移植部署（nix run . -- init gcd 一条命令建工程）。工程配置集中在 ecc.toml，flow.preset 支持 rtl2gds / rcx / harden / syn_sta 四档预设，可对既有工程改预设后 --overwrite 重跑。
本周合入（07-31 → 08-03）：
· #177 feat: add flow agent foundation（08-03 合入）——为流程层引入智能体地基，标志 ECC 从"脚本化流程运行器"向"可由 Agent 调度的流程引擎"演进；
· #184 feat: support soc-mpc template（08-03）——新增 SoC MPC（多项目晶圆）工程模板，直指国内高校/小团队最常见的 MPC 流片场景；
· #181 refactor：从综合输出中移除未使用的固定网表；#179 fix(ci)：CI 恢复到最新 ics55 PDK（ICsprout 55nm 国产开源 PDK）；#178：删除 ecc snapshot。
核心看点：与 agent-r2g「在 OpenROAD 之上套 Agent Skill」的路线不同，ECC 走的是"自研后端 + 国产 PDK + 智能体地基内建"的路线——PDK 侧绑定 ics55（对应本站此前收录的 OSCC iEDA / icsprout55-pdk 生态），流程侧用 Nix + TOML 把可复现性做进工具本身。两条路线合起来正好构成开源 AI-EDA 的两个方向：把智能体接到成熟开源流程上 vs 把智能体接口做进新流程的地基里。

✅ 全开源工具链的 LLM 形式验证 RTL 修复流水线：Yosys + SymbiYosys + Z3 反例引导迭代，k-归纳给出正确性证明——并诚实报告四类失败模式

验证消耗了现代芯片设计的大部分工作量，但能提供数学正确性保证的形式验证工具依然昂贵且授权受限。已有的 LLM RTL 修复工作，要么只用仿真验证结果（仅覆盖输入空间的子集），要么依赖商业工具，几乎没有工作把形式证明与完全开源的工具链结合。本文提出一个多智能体流水线，将 LLM 与开源形式后端（Yosys + SymbiYosys + Z3）耦合，通过反例引导迭代（CEGIS 式）修复 RTL：框架自动生成形式属性 → 验证设计 → 把反例回灌给 LLM，直到设计被 k-归纳（k-induction）证明正确或迭代预算耗尽。
结果：在 ALU 案例研究中，流水线检出并修复了一个真实功能 bug，并给出正确性的形式证明；在六个基准的套件上，有一个设计可被稳定修复——作者没有粉饰这个偏低的成功率，而是把工作明确定位为可行性研究 + 详尽失败分析，并刻画出四类失败模式：有界覆盖空洞（bounded-cover vacuity）、规格歧义、时序逻辑 bug、多属性压力。此外还向开源形式验证社区报告了 Yosys bind 指令的一项实用性限制。
核心创新与价值：这是本站近期收录的验证类工作中最"反宣传"的一篇——在 CircuitProver（Lean 4 全通过 63/63）、Rtl2lean、VeriRefine 等高分结果之外，它给出了另一侧的现实坐标：当形式后端从商业工具换成纯开源 Yosys/SymbiYosys/Z3、且不允许用仿真兜底时，LLM 修复 RTL 的真实成功率会掉到什么水平、卡在哪里。其中"有界覆盖空洞"（k-induction 深度不足导致证明看似通过实则空洞）与"多属性压力"（同时满足多条属性时 LLM 顾此失彼）两类失败，对所有做"验证器反馈闭环"的工作（VClare / MechMem-RTL / ContractHIL-HLS）都是必须正面回答的问题。对希望零成本复现 LLM+形式验证闭环的团队，本文的开源栈组合具有直接工程参考价值。
